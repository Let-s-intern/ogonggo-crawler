# 크롤러 등록 흐름

운영자가 목록 URL 하나를 넣으면 그 뒤에 무슨 일이 일어나는가.

등록에서 정해지는 것은 셋이다. 셀렉터(`crawlers.selectors_json`), 수집 모드
(`crawlers.list_mode` / `detail_mode`), API 설정(`crawlers.api_config_json`).

진입점은 `POST /api/crawlers` 다 (`app/api/crawlers.py`).

## 브라우저는 등록할 때만 열린다

주기 실행은 등록에서 알아낸 경로를 공용 fetch 클라이언트로 부를 뿐이고, 클릭도 렌더도 하지
않는다. 브라우저 인스턴스 하나가 150~300MB 이고 워크플로우가 시간 제한을 넘기는 주된 이유라,
그 비용을 실행마다 내지 않기 위해 등록 한 번으로 몰아 둔 구조다.

## 상세로 가는 길을 먼저 찾는다

`app/selector/discovery.py` 의 `discover_detail_path()` 가 네 단계를 순서대로 밟고, 앞
단계로 풀리면 뒤 단계는 하지 않는다.

| 순서 | 하는 일 | 다음으로 넘어가는 조건 |
|---|---|---|
| 1 | 목록을 `httpx` 로 받는다 | 항목이 없거나 상세 주소를 만들 값이 없다 |
| 2 | 렌더한다 | 렌더해도 항목에 상세 주소가 없다 |
| 3 | 항목을 클릭하고 그때 나가는 요청을 본다 | 클릭으로 상세에 도달했다 |
| 4 | 알아낸 요청을 `httpx` 로 다시 부른다 | 같은 응답이 오면 채택 |

브라우저를 여는 일은 이 함수가 직접 하지 않고 필요한 순간에 부르는 `open_probe` 로 받는다.
1번에서 끝나면 그것을 한 번도 부르지 않는다.

4번이 이 흐름의 핵심이다. 브라우저에서 본 것을 그대로 믿지 않고, 브라우저 없이 같은 것이
오는지 확인한 뒤에만 채택한다. 확인하지 않고 저장하면 그 사이트는 실행마다 브라우저가 필요한
채로 등록된다.

## 클릭 성공 판정이 "주소가 바뀌었나" 가 아니다

2026-08-25 측정에서 여섯 사이트의 클릭 결과가 넷으로 갈렸다
(`app/crawler/click_probe.py`).

| 신호 | 사이트 | 무슨 일이 있었나 |
|---|---|---|
| 주소가 바뀐다 | 롯데, LG, 한화 | 같은 탭에서 상세로 이동한다 |
| 새 탭이 열린다 | SK | 목록 탭은 그대로 있다 |
| 요청이 나간다 | 삼성 | 주소는 그대로고 `detail.data` 가 나간다 |
| 본문이 길어진다 | 삼성 | 모달이 열려 1,620자에서 9,798자가 됐다 |

주소만 보면 삼성이 실패로 읽힌다. 넷 중 하나라도 바뀌면 도달이고, 넷 다 없을 때만
`detail_unreachable` 이다.

누르면 안 되는 것도 있다. 현대는 항목의 첫 `a` 들이 SNS 공유 버튼이라 눌러도 아무 데도 가지
않는데, 실제로는 항목의 `data-` 속성으로 상세 주소를 만들 수 있다
(`.claude/site-recipes/talent-hyundai-com.md`).

목록이 채워진 뒤에 누른다. 삼성은 목록을 늦게 채워서, 항목 0건인 채로 누르면 "이동하지 않음"
으로 잘못 판정된다. 항목이 없는 것은 클릭 실패가 아니라 `list_empty` 다.

## 관찰한 요청을 설정으로 옮기는 자리가 셋이다

셋 다 모양이 같다. 관찰한 것을 설정으로 옮기고, 공용 fetch 클라이언트로 다시 불러 같은 것이
오는지 본 뒤에만 채택한다.

| 모듈 | 무엇을 찾는가 | 결과가 들어가는 곳 |
|---|---|---|
| `app/selector/list_api.py` | 목록을 그리려고 페이지가 스스로 낸 요청 | `api_config_json` 의 `list` |
| `app/selector/detail_path.py` | 클릭 뒤 그 공고를 지목해 나간 요청 | `api_config_json` 의 `detail` |
| `app/selector/link_probe.py` | 클릭이 데려간 주소의 공통 형식 | `selectors_json` 의 `list.link_template` |

`detail_path.py` 가 요청을 고르는 기준은 "공고 번호가 들어 있는가" 다. 페이지 하나가 내는
요청 중 대부분은 공통 설정·배너·추천 목록이고 어느 공고를 눌러도 같다. 항목에서 읽은 번호가
주소나 본문에 들어 있는 요청만이 그 공고를 지목한 요청이다.

번호가 될 만한 값은 셋에서 모은다. 링크의 마지막 경로 조각, 링크의 쿼리 값, 항목의 `data-`
속성이다.

`link_probe.py` 는 상세가 JSON API 가 아니라 그냥 HTML 문서인데 그 문서로 가는 주소를 항목이
`href` 로 들고 있지 않은 사이트를 위한 자리다. 두산의 `onclick="goDetail('1000361539', ...)"`
과 네이버의 `onclick="show('30005276')"` 가 그런 경우다.

목록이 API 로 오는 사이트가 렌더로 남으면 실행마다 브라우저가 하나씩 뜬다. 그래서
`list_api.py` 가 찾아내는 것 하나가 그 사이트의 실행 비용을 통째로 바꾼다.

## 셀렉터 생성

`app/selector/generator.py` 가 목록과 상세 HTML 을 모델에 보내 셀렉터 JSON 을 받는다.
어느 제공자를 쓸지는 설정이 정하고, 이 파일은 그것을 모른다
(`.claude/docs/llm-providers.md`).

보내기 전에 `app/selector/cleaner.py` 가 줄인다. `script`·`style`·`svg`·`noscript`·
`iframe`·`template` 과 주석, 인라인 이벤트 핸들러를 걷어내고, 반복 리스트는 형제 넷만 남긴다
(`DEFAULT_KEEP_SIBLINGS = 4`). 60개나 4개나 구조 신호는 같고 비용만 다르다.

상한(`DEFAULT_MAX_CHARS = 30000`)을 넘으면 무작정 자르지 않고 반복 영역으로 먼저 좁힌다.
좁혔다는 사실은 결과에 남아 응답에 실린다.

셀렉터 JSON 의 칸은 `app/selector/schema.py` 가 정한다.

| 구역 | 필수 | 선택 |
|---|---|---|
| `list` | `item` `title` `link` `date` | `company` `link_template` |
| `detail` | `title` `body` `requirements` `deadline` `department` | `company` 와 `SPLIT_DETAIL_FIELDS` 열 개 |

선택 칸이 전부 기본값을 갖는 이유는 하나다. 그 필드들이 생기기 전에 저장된 셀렉터 JSON 이
키 없이도 그대로 통과해야 한다.

검증은 통과 아니면 실패다. 스키마에 없는 필드명이 오면 무엇을 말하려던 것인지 추측해서 고치지
않는다 — 조용히 고친 셀렉터는 나중에 왜 안 맞는지 아무도 설명하지 못한다.

| reason | 뜻 |
|---|---|
| `unparsable` | JSON 이 아니거나, 객체·문자열이 아닌 자리에 다른 타입이 왔다 |
| `unknown_field` | 스키마에 없는 필드명이 왔다 |
| `missing_field` | 필수 필드가 없거나 값이 비어 있다 |

깨진 응답(`unparsable`)만 1회 재생성한다(`MAX_ATTEMPTS = 2`). 나머지 실패는 운영자에게
넘긴다.

## 생성한 셀렉터는 그 자리에서 돌려 본다

`app/selector/verify.py` 가 방금 가져온 그 HTML 에 즉시 적용해 매칭 개수를 센다. 0개 매칭
필드는 성공으로 내놓지 않고, 실패한 필드 이름을 그대로 결과에 넣는다.

`list.link` 만 판정 기준이 다르다. 노드 수가 아니라 따라갈 수 있는 URL 이 나오는지로 본다.
2026-08-22 에 한화에서 모델이 `list.link` 로 `h4.recruit-title` 을 골랐고, 노드 수만 세는
검증이 20/20 으로 통과시켰다. 통과한 셀렉터로 실행하니 링크가 없어 실패했다.

그래서 판정은 파서와 같은 `app/selector/link.py` 를 쓴다. 두 곳이 각자 판정하면 "검증은
통과했는데 실행은 실패한다" 가 생긴다.

목록 필드가 하나도 안 잡히는 것(`list_missing`)은 필드 하나가 틀린 것과 다르다. 그 페이지의
정적 HTML 에 목록 자체가 없다는 뜻이고 손으로 고칠 셀렉터가 없다.

여기서 하는 것은 "그 셀렉터가 노드를 잡는가" 까지다. 잡은 값이 깨끗한지는 정규화의 몫이고,
공백이나 광고 문구가 섞였다고 셀렉터를 바꾸지 않는다.

## 넓게 잡은 항목 셀렉터는 좁힌다

네이버 목록에서 `li.item` 은 144건 잡히고 그중 공고는 10건이다. 나머지는 필터와
네비게이션이다. 넓은 쪽을 그대로 저장하면 실행마다 공고가 아닌 항목 134건이 실패로 쌓인다.

`app/selector/narrow.py` 가 제목을 하나씩만 품는 반복 요소로 좁힌다. 후보는 둘이고,
`<모델이 낸 항목>:has(<제목>)` 을 먼저 본다 — 모델이 낸 셀렉터를 가장 적게 바꾸는 쪽이고,
항목 안에서 찾는 `link`·`date`·`company` 셀렉터가 그대로 살아 있어야 좁힌 것이 이득이 된다.

넓히지 않는다. 매칭이 늘어나는 방향으로는 절대 바꾸지 않고, 후보가 제목을 하나라도 빠뜨리면
그대로 둔다. 페이지 전체를 잡는 셀렉터는 조용히 실패하기 때문에 0개 매칭보다 나쁘다.

바꿨으면 무엇을 무엇으로 바꿨는지 문장으로 남긴다.

## 판정은 제안이고 저장은 운영자가 한다

`discover_detail_path()` 가 내놓는 `Discovery` 는 어디에도 저장되지 않는다. 여섯 사이트는
사람이 이미 확인해 설정해 뒀고, 그것을 자동 판정으로 덮어쓰지 않는다.

근거는 문장으로 남긴다. "정적 목록에 항목 0건, 렌더 후 16건, 항목에 상세 주소가 없어
클릭했다" 처럼 경로마다 다른 문장이다. 판정만 남기면 다음 사람이 왜 그렇게 정해졌는지 알 수
없어 처음부터 다시 재게 된다.

판정하지 못해도 등록은 남는다. 사유와 다음 행동이 화면에 적힌다.

## 셀렉터를 고치는 두 가지 길

손 편집이 첫 수단이다. 운영자가 크롤러 화면에서 직접 고치고
(`PUT /api/crawlers/{crawler_id}/selectors`), 그 값을 자동 생성이 덮어쓰지 않는다.

모델에게 다시 물을 수도 있다(`POST /api/crawlers/{crawler_id}/repair`,
`app/selector/repair.py`). 이 경로는 자동이 아니라 운영자가 누르는 버튼으로만 들어오고,
저장도 하지 않는다 — 고치기 전과 후를 나란히 돌려줄 뿐이다.

부를 때 두 가지 상황이 있다.

| 상황 | 모델에게 주는 것 |
|---|---|
| 실패한 필드가 있다 | 지금 셀렉터 전부와 실패한 필드의 사유 |
| 전부 잡고 있는데 값이 틀렸다 | 위에 더해 운영자가 브라우저에서 보고 적어 준 단서 |

두 번째가 있는 이유는 0개 매칭이 아니면 코드가 무엇이 틀렸는지 알 방법이 없어서다. F12 의
`Copy selector` 가 뱉은 경로여도 되고 값이 어디 있는지 설명하는 문장이어도 된다. 단서는
`MAX_HINT_CHARS = 800` 안으로 줄여서 보낸다.

## 테스트 실행

`POST /api/crawlers/{crawler_id}/test-run` 이 한 번 돌려 미리보기를 준다. `raw_jobs` 에
적재하지 않고 `crawl_runs.trigger` 는 `test` 다 (`.claude/docs/crawl-run.md`).

저장된 것을 바꾸지 않고 다른 모드로 한 번 돌려 볼 수 있다. 필드 매칭 개수가 모드를 바꿀지
말지를 정하는 근거이고, 알아낸 것은 사이트 레시피에 적는다 (`.claude/site-recipes/`).
