# 스케줄링과 워크플로우

무엇이 언제 도는가. 구현은 `app/scheduler.py` 와 `app/side/` 다.

APScheduler 가 API 프로세스 안에서 돈다. 브로커도 두 번째 프로세스도 없다
(`.claude/docs/tech-stack.md`).

## 표가 진실이다

스케줄러가 들고 있는 잡 목록은 테이블의 사본일 뿐이고, 둘이 어긋나면 테이블 쪽으로 맞춘다.

그래서 등록도 갱신도 `sync()` 하나로 한다. 기동할 때도, 주기나 상태가 바뀐 뒤에도 같은 함수를
부른다. "이 워크플로우만 다시 등록" 같은 부분 갱신 경로를 따로 두면 그 경로가 빠뜨린 변경이
스케줄러 메모리에만 남는다.

무엇을 실행할지도 잡이 아니라 테이블이 정한다. 잡에 실려 있는 것은 워크플로우 id 뿐이고,
URL 과 셀렉터는 실행 시점에 `app/crawler/runner.py` 가 다시 읽는다.

## 워크플로우가 두 종류다

| 표 | 무엇을 도는가 | 실행 기록 | 잡 id 앞머리 |
|---|---|---|---|
| `workflows` | 크롤러 하나를 크롤링한다 | `crawl_runs` | `workflow:` |
| `side_workflows` | 이미 수집한 공고를 처리한다 | `side_runs` | `side:` |

두 표는 저마다 자동 증가라 1번이 둘 있다. 그래서 잡 id 의 앞머리로 가른다.

한 번의 `sync()` 가 둘을 함께 맞춘다. 표 하나만 보는 동기화가 생기면 다른 표의 변경이
스케줄러에 늦게 온다.

부가 잡이 되는 것은 `side_workflows` 에서 `active` 이면서 `trigger_kind` 가 `interval` 인
행뿐이다.

## 왜 한 표에 합치지 않았나

셋이다.

`workflows.crawler_id` 는 `NOT NULL` 이고 분류에는 크롤러가 없다. 합치려면 그 제약을 풀어야
하는데, 그 순간 "워크플로우는 크롤러 하나를 돈다" 가 스키마에서 사라진다.

세는 것이 다르다. `crawl_runs` 는 신규·건너뜀·실패를 세고, 분류가 셀 것은 처리 건수와 버린
칸이고, 전달이 셀 것은 전송 건수다. 한 표에 넣으면 어느 컬럼이 어느 종류에서만 뜻이 있는지
아무 데도 적혀 있지 않게 된다.

이미 결정으로 서 있었다. `app/api/classify.py` 와 `app/normalize/backfill.py` 가
"`crawl_runs` 에 쓰지 않는다, 섞으면 워크플로우 성공·실패 통계가 크롤링과 무관한 이유로
움직인다" 를 근거로 들고 있다. `side_workflows` 는 그 결정을 스키마로 옮긴 것이다
(`migrations/0021_side_workflows.sql`).

## 부가 워크플로우의 설정

| 컬럼 | 받는 값 |
|---|---|
| `kind` | `classify` / `deliver`. 만들 때 정하고 나중에 바꾸지 않는다 |
| `status` | `active` / `paused`. 새로 만들면 `paused` 다 |
| `trigger_kind` | `interval` / `after_crawl` / `manual` |
| `target_scope` | `kind` 마다 다르다 |
| `target_days` | `recent` 일 때만 쓴다. 그 밖에는 NULL |
| `batch_limit` | 1회 상한 건수. 기본 50 |

`target_scope` 가 받는 값이 `kind` 마다 다르다.

| kind | 받는 범위 |
|---|---|
| `classify` | `unclassified`(기본) / `empty_fields` / `recent` / `all` |
| `deliver` | `undelivered`(기본) / `recent` / `all` |

둘을 합집합 하나로 두면 전달 워크플로우에 `unclassified` 가 들어가고, 그 행은 저장될 때가
아니라 실행할 때 대상을 못 찾아서 드러난다. 그래서 CHECK 가 `kind` 와 함께 본다.

`kind` 를 나중에 바꾸지 않는 이유도 같다. 종류가 바뀌면 `target_scope` 의 뜻이 같이 바뀌는데,
그때 이미 저장된 범위가 새 종류에서 무엇을 뜻하는지 정할 방법이 없다. 종류를 바꾸는 일은
지우고 다시 만드는 일이다.

새로 만들면 `paused` 인 것이 기본값에 들어 있다. 대상 범위를 잘못 고른 채 저장하는 것과
그것이 곧바로 도는 것은 다른 이야기고, `all` 은 640건이면 약 285만 토큰이다.

`batch_limit` 의 상한을 DB 에 두지 않는다. 그 값은 `app/classify/batch.py` 의 `MAX_LIMIT`
이고, 여기에 200 을 적으면 상한을 고치는 일이 마이그레이션이 된다. DB 는 1 미만만 막는다.

## 무엇이 실행을 깨우는가

`side_runs.trigger` 는 `crawl_runs.trigger` 와 같은 낱말을 쓰되 `test` 가 없다. 부가 작업에는
승격 전 크롤러 같은 것이 없다.

| trigger | 무엇이 깨웠나 |
|---|---|
| `schedule` | APScheduler |
| `after_crawl` | 크롤 실행이 새 공고를 적재한 직후 |
| `manual` | 화면에서 누른 것 |

`after_crawl` 은 `trigger_after_crawl()` 이 건다. 새 공고가 있을 때만이고, 실패해도 크롤
실행 결과를 바꾸지 않는다 (`.claude/docs/crawl-run.md`).

## 겹치지 않는다

크롤 워크플로우는 이미 실행 중이면 그 차례를 스킵하고 로그를 남긴다.

부가 워크플로우는 열린 `side_runs` 행이 있으면 돌고 있는 것으로 보고 `skipped` 행을 남긴다.
행을 남기지 않으면 주기가 도는데 아무것도 안 하는 상태와 주기가 죽은 상태가 같아 보인다.

이 판정이 기동 시 뒷정리와 맞물린다. 죽은 프로세스가 남긴 열린 행 하나가 그 워크플로우를
영영 막으므로, `close_orphans()` 가 기동할 때 열린 행을 닫는다 (`app/main.py` 의 `lifespan`).

## 동시 실행 상한

고정값이 아니라 어드민 화면에서 바꾸는 운영 설정이다 (2026-08-21 결정).

`.env` 의 `MAX_CONCURRENT_RUNS` 는 값이 아직 없을 때 한 번 넣어 주는 초기값이고, 그 뒤로는
`app_settings` 표가 진실이다. 값이 바뀌면 프로세스를 다시 띄우지 않고 다음 실행부터 새 상한이
적용된다. 이미 돌고 있는 실행은 끊지 않는다.

그래서 고정 크기 세마포어를 쓸 수 없다. `RunGate` 가 자리를 얻을 때마다 현재 값을 다시 읽는다.

읽고 쓰는 곳은 `app/settings.py`, 상한을 실제로 거는 곳은 `app/scheduler.py` 다.

## 실행 기록이 없는 실행이 없어야 한다

두 종류 다 행은 실행이 시작할 때 생기고 종료 상태 없이 열려 있다. 끝날 때 상태와 카운트로
닫는다.

끝나고 나서 한 번에 적으면, 도는 도중에 프로세스가 사라진 실행은 아무 데도 남지 않는다.
그리고 그런 실행이야말로 무엇이 있었는지 알아야 하는 실행이다.

닫는 경로가 셋이다. 정상 종료, 예외, 그리고 프로세스가 사라진 뒤의 기동 시 뒷정리다.

부가 실행은 토큰을 세지 않는다. `llm_calls` 가 호출마다 남기고 있고, 같은 숫자를 두 곳에서
세면 어느 쪽이 진실인지 매번 확인해야 한다 (`.claude/docs/llm-providers.md`).

## 예외 없이 실패하는 실행이 있다

제공자 키가 없으면 `app/classify/batch.py` 는 예외를 올리지 않고 진행 상황에 사유를 적고
돌아온다. 그 실행은 `failed` 로 닫히면서 사유가 `error_message` 에 남는다.

그리고 부가 실행은 예외를 다시 올리지 않는다. 이 함수를 부르는 것은 스케줄러와 API 스레드라,
거기까지 올라간 예외는 아무도 보지 못한 채 잡을 죽인다. 실행 하나가 실패한 것은 행에 적혀야
할 사실이지 호출자가 처리할 예외가 아니다.
