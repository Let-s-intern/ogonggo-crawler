# 크롤러 → 오공고 백엔드 전달 설계

크롤링 서버가 수집·정규화한 채용공고를 오공고 백엔드로 보내는 방식을 정리한 문서다.
**오공고 백엔드 담당자와 함께 읽는 것을 전제로 쓴다.**

아직 구현 전이다. 양쪽 스키마를 대조한 결과와, 구현 전에 합의가 필요한 항목을 담았다.

## 배경

크롤링 서버는 채용 사이트를 주기적으로 크롤링해 공고를 모으고, 본문을 분류해 필드를 채운 뒤
`normalized_jobs` 에 저장한다. 그 결과를 오공고로 넘기는 것이 이 문서의 범위다.

크롤링 서버는 원래 **오공고가 가져가는 방식**(폴링)을 전제로 조회 API 를 열어 두었다
(`GET /api/jobs`). 그런데 오공고에 `POST /api/v1/internal/jobs` 가 이미 만들어져 있고
`X-Internal-Api-Key` 로 서버 간 인증까지 끝나 있어, **크롤링 서버가 보내는 방식**으로 맞추려
한다.

조회 API 는 그대로 둔다. 다른 소비 측이 생길 수 있고, 무엇을 보냈는지 사람이 확인하는
자리이기도 하다.

## 크롤링 서버가 부를 곳

```
POST /api/v1/internal/jobs
X-Internal-Api-Key: <키>
Content-Type: application/json
```

응답을 이렇게 해석할 예정이다. 틀린 부분이 있으면 알려 주기 바란다.

| 응답 | 해석 | 크롤링 서버의 동작 |
|---|---|---|
| `200` | 등록됨 | 전달 완료로 기록한다 |
| `409` `JOB_ALREADY_EXISTS` | 같은 `sourceUrl` 이 이미 있다 | 성공으로 본다. 재시도하지 않는다 |
| `401` | 키가 없거나 다르다 | 설정 문제로 보고 재시도하지 않는다 |
| `400` | 검증 실패 | 보낸 값의 문제로 보고 재시도하지 않는다 |

중복 판정이 `sourceUrl` 하나이므로 **같은 URL 의 공고는 최초 1회만 등록된다.** 공고 내용이
바뀌어도 갱신되지 않는다는 뜻인데, 이대로 두는 것이 맞는지 확인이 필요하다.

### 크롤링 서버에 있고 오공고에 없는 것 (5칸)

보내지 않는다. 필요하면 오공고에 칸을 만드는 것을 논의할 수 있다.

| 크롤링 서버 | 어떤 값인가 | 왜 안 보내나 |
|---|---|---|
| `body` | 공고 본문 전체를 평문으로 편 것 | 오공고가 본문을 일곱 칸으로 나눠 받는다. 통짜 본문을 담을 칸이 없다 |
| `etc_info` | 일곱 칸에 들어가지 않은 나머지 안내 | 같은 이유 |
| `job_role` | 제목에서 뽑은 직무명. 자유 텍스트 | 오공고에 직무 칸이 없다 |
| `job_major` | 직무 대분류. 닫힌 목록 | 아래 `tags` 절 |
| `job_minor` | 직무 소분류. 닫힌 목록 | 아래 `tags` 절 |

### 오공고에 있고 크롤링 서버에 없는 것 (5칸)

항상 비워서 보낸다. 크롤링 서버가 만들지 않는 값이다.

| 오공고 | 크롤링 서버가 못 채우는 이유 |
|---|---|
| `companyAndTeamIntroduction` | 본문을 나눌 때 이 항목을 따로 두지 않았다 |
| `compensation` | 같음 |
| `benefits` | 같음 |
| `educationLevel` | 학력 조건을 판정하지 않는다. 생략하면 오공고가 `ANY` 로 채운다 |
| `tags` | 아래 절 |

### tags 를 비우는 이유

크롤링 서버에 `job_major`·`job_minor` 라는 직무 분류가 있지만 `tags` 로 보내지 않기로 했다
(2026-09-08).

두 값은 크롤링 서버 DB 의 `job_taxonomy` 표에서 고르는 닫힌 목록이고, 그 목록은 배포 없이
바뀐다. 태그 문자열로 넘기면 오공고에 분류 체계가 복제되고, 목록을 고칠 때마다 이미 보낸
것과 어긋난다.

직무 분류를 오공고에서 쓸 필요가 있다면 태그가 아니라 전용 필드로 논의하는 편이 낫다.

## 오공고가 값에서 유도하는 것

크롤링 서버가 보내지 않아도 오공고가 정하는 값이다. 코드를 읽고 파악한 것이라 확인이 필요하다.

```
experienceType     경력 연수가 둘 다 없으면 IRRELEVANT, 있으면 EXPERIENCED
recruitmentType    모집 일시가 둘 다 없으면 ALWAYS_OPEN, 있으면 PERIOD
publicationStatus  항상 PUBLISHED
```

`publicationStatus` 가 `PUBLISHED` 고정이면 **전달하는 즉시 사용자에게 노출된다.** 크롤링
서버에는 사람이 값을 확인하는 검수 화면이 있는데, 검수 전 공고를 보내면 그대로 공개된다는
뜻이다. 이 동작이 의도한 것인지 확인이 필요하다.

## employment_type 매핑

크롤링 서버의 고용형태는 닫힌 목록이다. 분류가 본문을 읽고 이 넷 중에서 고르며, 목록에 없는
값은 저장되지 않는다.

| 크롤링 서버 | 오공고 |
|---|---|
| 정규직 | `FULL_TIME` |
| 계약직 | `CONTRACT` |
| 인턴 | `INTERN` |
| 기타 | `ETC` |
| `null` | 합의 필요 |

오공고의 `PART_TIME` 에 해당하는 값을 크롤링 서버가 만들지 않는다.

`null` 은 "본문만으로 판단할 수 없었다" 는 뜻인데 오공고에서는 필수 필드다. 두 안이 있다.

| 안 | 성질 |
|---|---|
| 보내지 않는다 | 아래 전송 기준에 자연히 걸린다 |
| `ETC` 로 보낸다 | "기타" 와 "모름" 이 오공고에서 구분되지 않는다 |

## career_level — 오공고에 요청할 것

**그대로 보내면 값이 뒤집힌다.**

크롤링 서버의 경력 구분은 `신입` / `경력` / `무관` / `null` 이고 오공고는 경력 연수 숫자를
받는다. 그런데 오공고는 그 숫자로 `experienceType` 을 유도한다 — 값이 있으면 `EXPERIENCED` 다.

그래서 `신입` 을 `experienceMinYears = 0, experienceMaxYears = 0` 으로 보내면 오공고에서
**경력 공고가 된다.**

**`experienceType` 을 직접 받는 필드를 추가해 주기를 요청한다.** 오공고에 이미
`NEWCOMER`/`EXPERIENCED`/`IRRELEVANT` enum 이 있고, 요청 DTO 가 숫자만 받는 것이 원인이다.
필드 하나를 더하면 크롤링 서버 값이 그대로 들어가고 변환이 필요 없어진다.

추가가 어렵다면 `career_level` 을 보내지 않는다. 그 경우 모든 공고가 `IRRELEVANT`(경력무관)가
된다.

## 시각 표기 — 합의 필요

크롤링 서버는 마감일과 시작일을 **`YYYY-MM-DD` 문자열**로 저장한다. 시각이 없고 시간대도 없다.

오공고는 `LocalDateTime` 을 받는다. 시각을 붙여야 하는데 어떻게 붙일지 정해야 한다.

- 마감일에 `00:00` 을 붙이면 그날 하루가 통째로 지난 것이 된다. 마감일은 그날 끝으로 보는
  편이 뜻에 맞다
- 시간대를 정하지 않으면 아홉 시간이 어긋난다. 마감일이 하루 밀리거나 당겨지는 오차라
  조용히 틀린다

오공고가 이 값을 어느 시간대로 읽는지 알려 주면 거기에 맞춘다.

## 전송 기준

**13칸 중 8칸 이상 채워진 공고만 보낸다**(60%, 2026-09-08 결정).

비어 있는 칸이 많은 공고를 보내면 사용자가 열어 보고 아무것도 없는 화면을 만난다.

세는 대상은 위 "양쪽에 다 있는 것" 13칸이다. 오공고가 받지만 크롤링 서버가 채우지 않는 다섯
칸은 빼고 센다 — 넣으면 아무리 잘 뽑아도 상한이 72% 라 기준이 뜻을 잃는다.

필수 4칸은 없으면 어차피 못 보내므로, 실질적으로 **선택 9칸 중 4칸 이상**이다.

`career_level` 을 보내지 않기로 하면 12칸이 되고 기준은 8칸 그대로다.

이 기준은 값이 있는지만 본다. 내용이 쓸 만한지는 판단하지 않는다.

## 크롤링 서버의 값이 어떻게 만들어지나

오공고 쪽에서 받는 값의 성격을 알아야 하는 부분이다. 칸 이름만 보고 짐작하면 어긋난다.

`normalized_jobs` 의 값은 출처가 셋이다.

| 출처 | 뜻 |
|---|---|
| 수집 | 페이지에서 CSS 셀렉터로 뽑고 정규화 규칙을 지난 값 |
| 판정 | 본문을 모델에 넣어 **닫힌 목록에서 고른** 값 |
| 추출 | 본문을 모델에 넣어 **뽑아 적은** 자유 텍스트 |

세 경우 모두 값이 없으면 NULL 이다.

| 칸 | 출처 | 저장된 모양 | 알아야 할 것 |
|---|---|---|---|
| `company` | 수집 | 자유 텍스트 | 공고가 말한 자회사다. 사이트가 주지 않으면 NULL |
| `parent_company` | 수집 | 자유 텍스트 | 크롤러 설정에서 온다. 그 채용 사이트를 운영하는 기업이다 |
| `title` | 수집 | 자유 텍스트 | |
| `source_url` | 수집 | URL | 항상 있다 |
| `deadline` | 수집 | `YYYY-MM-DD` | 시각도 시간대도 없다 |
| `start_date` | 수집 | `YYYY-MM-DD` | 사이트가 시작일을 안 주는 곳이 많아 NULL 이 흔하다 |
| `employment_type` | 판정 | `정규직` `계약직` `인턴` `기타` | 이 넷뿐이다 |
| `career_level` | 판정 | `신입` `경력` `무관` | 이 셋뿐이다 |
| `work_location` | 추출 | 자유 텍스트 | |
| `duties` | 추출 | 자유 텍스트 | |
| `requirements` | 추출 | 자유 텍스트 | |
| `preferred` | 추출 | 자유 텍스트 | |
| `hiring_process` | 추출 | 자유 텍스트 | |

### 회사명이 두 칸이다

`company` 는 **그 공고가 말한 자회사**이고 `parent_company` 는 **그 채용 사이트를 운영하는
기업**이다. 한 칸에 둘이 겹쳐 앉아 있어 2026-08-28 에 갈랐다.

그룹 채용 사이트에서 계열사 공고를 수집하면 `parent_company` 가 그룹, `company` 가 계열사다.
사이트가 계열사를 밝히지 않으면 `company` 가 NULL 이다.

### 값을 못 정하면 NULL 이다

판정 칸 둘은 모델이 "판단불가" 를 낼 수 있고, 그 답은 저장 전에 NULL 이 된다.

`employment_type` 이 NULL 인 것은 오류가 아니라 **본문에 판단할 근거가 없었다**는 뜻이다.
오공고에서 이 칸이 필수라는 점과 맞물리는 지점이라 위 매핑 절에서 합의가 필요하다.

### 본문에서 나오는 칸이 많다

추출 칸 다섯(`work_location` `duties` `requirements` `preferred` `hiring_process`)은 사이트에서
각각 뽑는 것이 아니라 **본문 하나를 나눠서** 채운다. 사이트마다 칸을 지정하는 방식이 640건에서 절반도
채우지 못했기 때문에 2026-08-26 에 바꾼 것이다.

그래서 본문을 못 가져온 공고는 이 칸들이 통째로 빈다. 전송 기준을 못 넘기는 공고는 대개
그런 경우다.

## 합의가 필요한 항목

| 항목 | 내용 |
|---|---|
| `experienceType` 필드 | 오공고 요청 DTO 에 추가 요청. 없으면 신입 공고가 경력으로 뒤집힌다 |
| 시각 표기 | 날짜에 시각을 어떻게 붙일지, 어느 시간대로 볼지 |
| `employment_type` 이 NULL 인 공고 | 보내지 않을지, `ETC` 로 보낼지 |
| `publicationStatus` 고정 | 전달 즉시 공개되는 것이 의도한 동작인지 |
| `sourceUrl` 중복 시 갱신 | 최초 1회만 등록되는 것이 맞는지 |
| 전달 주기 | 크롤링 직후인지, 별도 주기인지, 사람이 누르는지 |

## 크롤링 서버 쪽에 남은 구현

오공고 담당자가 볼 필요는 없는 항목이다. 크롤링 서버 안에서 처리한다.

- `app/deliver/` 에 설정만 있고 전송 코드가 없다. 변환·기준 판정·응답 처리·전달 기록이 필요하다
- `deliver_auth_header` 에 마스킹이 없다. 화면이 키를 그대로 그린다
  (`app/templates/fragments/deliver_form.html:40`). `app/storage/settings.py` 와 같은 방식으로 가린다
- `.claude/rules/crawling.md` 가 직접 HTTP 호출을 `app/notify/` 와 `app/storage/` 둘로 제한한다.
  `app/deliver/` 가 세 번째가 되므로 같은 커밋에서 고친다
- `.claude/docs/api-contract.md` 가 폴링 전제로 쓰여 있다. 같은 커밋에서 고친다
