# 크롤링 실행 흐름

워크플로우 하나가 한 번 도는 동안 무슨 일이 일어나는가.
구현은 `app/crawler/runner.py` 이고, 이 문서는 그 파일이 왜 그 순서인지를 적는다.

`crawl_runs` 행 하나가 실행 하나다. 행이 없는 실행은 아무도 디버깅하지 못한다.

## 실행을 시작하는 자리가 셋이다

| 부르는 곳 | 함수 | `crawl_runs.trigger` |
|---|---|---|
| 스케줄러 | `run_workflow()` | `schedule` |
| 화면의 1회 실행 | `run_workflow(trigger=MANUAL)` | `manual` |
| 등록 화면의 테스트 실행 | `run_once()` | `test` |

셋을 가르는 이유는 "주기가 실제로 도는가" 에 답하기 위해서다. 최근 실행이 있어도 그것이
사람이 누른 것이면 주기는 죽어 있다.

테스트 실행은 `workflow_id` 가 없다. 적재할 워크플로우가 없어서 `raw_jobs` 에 넣지 않고
미리보기만 돌려주며, 그 실행의 `new_count` 는 항상 0 이다.

## 실행할 값은 매번 표에서 다시 읽는다

`run_workflow()` 가 받는 것은 `workflow_id` 하나뿐이다. 목록 URL, 셀렉터, 수집 모드,
API 설정은 그 자리에서 `workflows` 와 `crawlers` 를 조인해 읽는다.

스케줄러가 잡을 등록할 때의 값을 들고 있다가 쓰지 않는다. 운영자가 화면에서 셀렉터를 고친 뒤
다음 실행이 옛 셀렉터로 도는 일을 만들지 않기 위해서다.

## 순서

```
1  설정 읽기        workflows + crawlers 조인. 셀렉터·API 설정 검증
2  수집기 열기      list_mode / detail_mode 로 목록·상세 수집기를 만든다
3  crawl_runs 시작  행을 열고 asyncio.timeout 으로 감싼다
4  목록 파싱        matched 와 항목별 파싱 실패를 센다
5  마감 거르기      목록 날짜가 오늘보다 이전이면 상세를 열지 않는다
6  신규 판정 1차    source_url 이 이미 있으면 상세를 열지 않는다
7  상세 수집        본문이 비면 적재하지 않고 실패로 남긴다
8  신규 판정 2차    content_hash 로 마지막 확인
9  raw_jobs 적재    append-only
10 정규화           적재한 건만. 실패해도 실행을 죽이지 않는다
11 crawl_runs 종료  상태와 카운트 다섯을 한 트랜잭션으로 쓴다
12 알림 / 분류 연쇄  새 공고가 있을 때만
```

어떤 경로로 끝나든 11번은 실행된다. 예외로 끝나도, 시간 제한에 걸려도, 밖에서 취소돼도 행은
닫힌다.

## 신규 판정을 두 번 하는 이유

`content_hash` 는 `source_url`·`title`·`deadline`·`body` 넷으로 만드는데
(`app/crawler/hashing.py`), `body` 와 `deadline` 은 상세에서 온다. 상세를 가져오기 전에는
해시를 만들 수 없다.

그래서 목록 단계에서는 `source_url` 하나로만 아는 공고인지 보고, 아는 공고면 상세 요청을
아예 보내지 않는다. 상세까지 간 건에 대해서만 해시를 만들어 마지막으로 한 번 더 확인한다.

앞의 판정이 없으면 이미 아는 공고 수백 건에 매 실행마다 상세 요청이 나간다.

## 본문이 없는 공고는 적재하지 않는다

상세를 열었는데 본문이 비면 그 공고는 `raw_jobs` 에 들어가지 않는다. 목록에서 읽은 값만
넣고 성공으로 넘기면 `body` 가 빈 행이 쌓이고, 소비 측은 그것을 본문 없는 공고로 받는다.

대신 어느 공고를 왜 놓쳤는지가 `crawl_run_failures` 에 제목과 함께 남는다. 건수만 남기면
고칠 수가 없다.

## 실패 분류

`error_class` 가 여섯인 이유는 조치가 각각 다르기 때문이다. 값을 정하는 곳은
`app/crawler/failures.py` 하나이고, `crawl_runs.error_class` 와 `crawl_run_failures.reason`
의 CHECK 제약이 같은 목록을 쓴다.

| error_class | 무슨 일이 있었나 | 조치 |
|---|---|---|
| `transport` | 타임아웃, 5xx, 연결 끊김 | 백오프 재시도. 반복되면 사이트 상태 확인 |
| `selector_miss` | 가져왔는데 item 이 0개 매칭 | 재시도 금지. 셀렉터 재작성 |
| `parse` | 매칭은 됐는데 필드를 못 읽었다 | 그 필드 셀렉터만 보정 |
| `list_empty` | 목록에서 반복 항목을 못 잡았다 | 목록 셀렉터나 목록을 얻는 방식을 고친다 |
| `detail_unreachable` | 링크·속성·클릭 어느 것으로도 상세에 못 갔다 | 상세 경로를 다시 찾는다 |
| `detail_empty` | 상세에 갔는데 본문이 비었다 | 본문 셀렉터만 보정 |

뒤의 셋이 공고 하나가 상세에 도달하지 못한 경우를 가른다. 셋을 합치면 "목록을 못 읽었다" 와
"본문 셀렉터가 틀렸다" 가 같은 값으로 남아 조치가 갈리지 않는다.

분류를 모르는 예외는 `parse` 로 밀어 넣지 않는다. `error_class` 를 NULL 로 두고 예외 이름을
`error_message` 에 남긴다. 모르는 실패를 아는 실패로 위장하면 그 사이트를 계속 잘못 고치게
된다.

## 카운트를 네 개로 나눠 센다

`crawl_runs` 에 저장되는 것은 넷이다.

| 컬럼 | 무엇을 세는가 |
|---|---|
| `success_count` | 오류 없이 처리를 마친 항목 수 |
| `new_count` | `raw_jobs` 에 실제로 넣은 수 |
| `fail_count` | 처리하다 실패한 수 |
| `skipped_count` | 마감이 지났거나 이미 아는 공고라 넘긴 수 |

목록 셀렉터가 잡은 항목 수(`matched`)는 `RunResult` 와 종료 로그 줄에만 있고 표에 남지
않는다. 미리보기와 진단이 읽는 값이다.

`skipped_count` 를 `fail_count` 에 합치면 안 된다. 합치면 마감 날짜 형식이 바뀌어 전부
걸러진 사이트가 "새 공고 0건" 인 정상 실행으로 보인다. 화면도 두 숫자를 나눠 적는다.

## 정상 파싱 0건은 실패다

예외 없이 끝났더라도 처리한 항목이 하나도 없으면 `failed` 다
(`app/crawler/failures.py` 의 `run_status()`).

항목별 실패가 있으면 그 분류를 그대로 쓰고, 그것조차 없으면 `list_empty` 다 — 목록이 쓸
항목을 하나도 내놓지 않은 것이라 고칠 자리는 목록 셀렉터나 목록을 얻는 방식이다.

실패로 적지 않으면, 사이트가 마크업을 바꾼 실행과 새 공고가 없는 실행이 같은 행으로 보인다.

## 정규화가 실패해도 수집은 남는다

정규화 규칙은 실행 시작에 한 번 읽는다. 실행 중간에 규칙이 바뀌어도 한 실행 안에서는 같은
규칙이 적용된다.

규칙 설정이 깨져 있으면 그 실행의 정규화는 전부 실패하지만 수집은 그대로 진행한다. 수집을
멈추면 규칙을 고쳐도 그 사이의 공고는 사라지고 없다. 실패한 건은 `raw_jobs` 에 그대로 남아
재정규화로 복구된다 (`.claude/docs/normalization.md`).

## 첫 실행만 건수를 막는다

등록하면 목록에 걸린 과거 공고가 통째로 들어온다. 2026-08-26 에 열두 곳을 등록하며 670건이
그렇게 들어왔고, 그 뒤 실행은 신규 0~1건이다.

저장량과 분류 토큰이 튀는 자리가 평소 수집이 아니라 이 첫 실행이라, 막을 곳도 여기 하나다.
상한은 `app_settings` 의 `first_run_limit` 이고 어드민에서 바꾼다.

두 번째 실행부터는 걸지 않는다. 상한이 계속 있으면 목록이 상한보다 길게 밀린 날에 뒤쪽 공고를
영영 못 본다 — 목록에서 밀려난 공고는 다시 올라오지 않는다.

실패한 실행은 첫 실행으로 세지 않는다. 판정은 `new_count > 0` 인 실행이 있었는가로 한다.
셀렉터가 틀려 0건으로 끝난 뒤 고쳐서 다시 도는 것이 흔한데, 그때 상한이 풀려 있으면 백필을
막으려던 것이 그대로 새어 나간다.

## 연속 실패는 자동으로 멈춘다

실행이 끝나면 `workflows.success_count` / `fail_count` 를 올린다. 이것은 항목 수가 아니라
실행 횟수다 — 화면 배지가 묻는 것은 "이 워크플로우가 몇 번 실패했나" 다.

성공이 아닌 것은 전부 실패로 센다. `timeout` 도 마찬가지다. 끝나지 못한 실행을 성공으로 세면
자동 중지가 영원히 걸리지 않는다.

`workflows.auto_stop_threshold` 만큼 연속 실패하면 상태를 `paused` 로 바꾼다. 임계치가 NULL
이면 자동 중지하지 않는다.

연속 실패 횟수는 따로 저장하지 않고 `crawl_runs` 에서 센다. 세는 곳과 기록하는 곳이 갈리면
화면이 말하는 연속 실패와 실제로 멈추는 시점이 어긋난다.

## 시간 제한

실행 하나를 `RUN_TIMEOUT_SECONDS` 로 감싼다. 끝나지 않는 실행 하나가 동시 실행 자리를 영원히
붙들고 있으면 나머지 워크플로우가 전부 멈춘다.

제한을 넘긴 실행은 `status=timeout` 으로 남고, 그때까지 적재한 `raw_jobs` 는 지우지 않는다.
append-only 라 되돌리지 않고, 다음 실행이 같은 공고를 다시 넣지도 않는다.

안쪽에서 올라온 `TimeoutError`(사이트가 응답하지 않은 것)와 제한을 넘겨 끊긴 것을 가른다.
앞을 `timeout` 으로 적으면 사이트 문제를 실행 시간 문제로 잘못 읽게 된다.

## 프로세스가 죽으며 남긴 행

SIGKILL 이나 컨테이너 재시작은 코드가 종료를 받아 적을 기회를 주지 않는다. 그러면
`crawl_runs` 행이 종료 상태 없이 남는다.

기동할 때 `close_orphan_runs()` 가 열린 행을 전부 `timeout` 으로 닫는다
(`app/main.py` 의 `lifespan`). 부가 워크플로우도 같은 뒷정리를 받는데, 그쪽은 화면 표시만의
문제가 아니다 — 겹침 방지가 "열린 행이 있으면 돌고 있는 것" 으로 판단하므로 죽은 프로세스가
남긴 행 하나가 그 워크플로우를 영영 막는다.

## 실행 뒤에 이어지는 것

둘 다 실패해도 실행 결과를 바꾸지 않는다.

`notify_new_jobs()` 가 새 공고를 ntfy 로 한 번 알린다. 건너뜀이나 실패는 알리지 않는다
(`.claude/docs/integrations.md`).

`trigger_after_crawl()` 이 `after_crawl` 로 걸린 분류 워크플로우를 잇는다. 새 공고가 있을
때만이다 (`.claude/docs/scheduling.md`).
